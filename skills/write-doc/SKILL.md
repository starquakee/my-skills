# Write Doc

写读者能直接使用的文档。结构跟着读者任务走，语言提供事实和操作，不写写作思路，不展示规则，不评价自己的成稿。

## 工作流程

1. **确定读者和结果**：读者是谁，读完后要完成什么。优先从现有材料判断；缺少的信息会影响成稿时再问，不为流程追问。
2. **核对事实**：从需求、代码、产品界面或官方资料提取命令、参数、版本、限制和链接。不猜测，不编造效果数据。读取或写入飞书文档时使用 `lark-doc` skill。
3. **安排主线**：先让读者完成最小任务，再展开常见场景、异常处理和参考资料。章节顺序按使用顺序排列，不按材料来源排列。
4. **写出完整成稿**：给出必要步骤、示例、验证方法和限制，不停留在提纲。用户只要正文时，直接交付正文。
5. **删减并复查**：先删重复和无效章节，再改长句、套话和空泛判断。简短不能以缺少前提、风险或验证方法为代价。

## 组织结构

- 标题说明对象和读者能得到的结果，如“用 X 完成 Y”，不用“关于 X 的详细介绍”。
- 开头直接说明它是什么、适合谁、用来做什么。只保留理解或使用所需的背景。
- 操作文档尽早进入第一步。安装、权限、登录等准备条件集中写清，避免读者操作到一半才发现缺项。
- 每节只回答一个问题。标题优先写具体任务或场景，如“定时运行任务”“更新后没有生效”，少用“概述”“其他”“相关说明”。
- 正文最多三级标题。能用一段说清就不拆小节，能用一句说清就不拆列表。
- 有序列表用于顺序不能打乱的步骤，无序列表用于并列项，表格用于比较有规律的数据。不要把所有段落都改成列表或表格。
- 同一规则只写一次。后文需要时引用前文，不换个说法重复。
- 常见问题写真实的使用障碍：具体现象、原因、处理动作。不要用 FAQ 重复产品卖点。
- 命令速查、完整参数和参考链接放附录，避免打断主线。

## 快速上手与使用指南

按内容需要选用下面的结构，不保留空章节，也不为了套模板增加内容：

```markdown
# [产品或功能] 快速上手：[完成的具体任务]

## 背景
[它是什么，适合谁；本文帮读者完成什么。]

## 快速跑通
### 准备工作
[依赖、权限、安装和登录。]

### 完成第一个任务
[最短操作路径、可复制的命令或指令、验证结果的方法。]

## 常见场景
### [具体场景]
[适用条件、操作或指令、关键限制。]

## 常见问题
**[具体现象]**
[原因和解决办法。]

## 附录
[命令速查、参数说明和参考链接。]
```

其他文档按目的重组。例如技术方案通常写“背景与目标、方案、关键流程、兼容性、验证、风险”，不硬套快速上手结构。

## 写好每一步

- 使用明确的主语和动词，直接说“谁做什么”。能主动表达就不连用被动句。
- 每句保留一个主要意思；背景、条件、动作和结果挤在一个长句里时拆开。
- 术语第一次出现时给出必要解释，后文沿用同一名称，不随意换简称。
- 步骤包含操作位置和具体动作。命令、代码和参数必须可复制，占位符用 `<agent_id>` 等明确形式。
- 关键步骤后说明如何确认成功。可能失败或产生副作用时，在原步骤旁写清后果和处理方式，不集中留到文末。
- 示例服务于当前任务，提供输入、操作和预期结果，不写无法运行的伪示例。
- 截图只用于定位界面或核对结果，并写清图意。链接使用能说明目的地的文字。
- 粗体用于步骤名、关键限制和故障现象；提示块用于必须注意的风险或可直接使用的指令。不要句句加粗，不用装饰性 emoji。

## 去除 AI 语气

- 删除“在当今……时代”“随着……的发展”“本文旨在”“总而言之”“希望本文能帮助你”等不提供信息的开场和结尾。
- 不用“赋能”“助力”“深度融合”“强大”“完美”“无缝”“极大地提升”等词代替事实。说明具体变化；能量化时给出依据，不能量化时写清少了哪一步、多了什么能力。
- 删除机械的“首先、其次、再次、最后”。步骤本身有顺序时直接编号。
- 不连续使用“不是……而是……”“不仅……更……”和相同句式的排比。需要纠正误解时直接写正确结论。
- 删除“值得注意的是”“需要特别强调的是”等提醒前缀，直接写风险、条件或要求。
- 少用破折号串联信息，少用反问和口号，不为每节补一段总结。

## 交付前检查

- 读者能凭正文完成任务，不需要猜入口、前提或下一步。
- 第一个可执行任务足够靠前，背景没有挤占操作内容。
- 命令、参数、名称、链接和限制有依据；未确认的信息已询问或明确标出。
- 关键步骤有验证方法，常见失败有处理入口。
- 每段都提供新信息，没有同义重复、空泛评价和自我总结。
- 标题、列表、粗体、代码块、表格和提示块都在表达实际结构。
